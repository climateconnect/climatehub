# Backend Development

This is the canonical reference for backend development on Climate Connect: how to set up your local environment, how to manage venvs across Python and Django upgrades, how to run tests, and how to handle common breakage. If something here is wrong or missing, please update it; this file is meant to grow.

For backend tech stack and Django/DRF patterns, see [`backend/agent.md`](../backend/agent.md).
For the in-flight Django 5.2 upgrade (in progress at time of writing), see `doc/spec/20260811_0843_upgrade_django_to_5_2_lts.md`.

---

## Quick start

```bash
# 1. Clone and enter the repo
cd climateconnect

# 2. Easiest path: open in VS Code and use the dev container
#    (Command Palette -> "Dev Containers: Reopen in Container")
#    The dev container provisions PostgreSQL 15 + PostGIS 3.3 + Redis 7 + Python 3.12.

# 3. Inside the dev container or on your local machine:
cd backend
pdm install                              # creates backend/.venv and populates it from pdm.lock
pdm run python -c "import django; print(django.get_version())"   # verify
pdm run python manage.py migrate
pdm run python manage.py test --keepdb   # run the test suite
```

The default Django version is whatever `pyproject.toml` resolves to on the current branch. As of 2026-08-11, that is **Django 5.2** (newly upgraded from 4.2 LTS).

## The venv-per-Django-major pattern

We **strongly recommend** keeping separate venvs per Django major version (one for `4.2.x`, one for `5.2.x`) rather than upgrading a single venv in place. The pattern has been in use at Climate Connect since the 3.x to 4.x upgrade; it lets you switch branches and run the matching test suite without rebuilding the venv every time you change branches.

### Why

- A `pdm.lock` for the Django 4.2 branch resolves Django 4.2 and a specific set of supporting package versions. A `pdm.lock` for the Django 5.2 branch resolves Django 5.2 and a *different* set of supporting versions. The two lockfiles are not interchangeable.
- If you upgrade a single venv in place when you pull the 5.2 branch, your old 4.2 branches will silently use 5.2-deprecated APIs and may pass tests that should be failing.
- Two venvs lets you `git checkout` between the 4.2 branch and the 5.2 branch without any re-install. The PDM venv name convention encodes which is which.

### Naming convention

The convention, encoded in `AGENTS.md`:

- `pdm venv activate django4` - the venv bound to the `Django~=4.2.x` branch.
- `pdm venv activate django5` - the venv bound to the `Django~=5.2.x` branch.

If we ever upgrade to Django 6.2 LTS, add `pdm venv activate django6`. Keep the old venvs around until every branch that uses them is merged and deleted.

### Workflow

On the 5.2 branch:

```bash
cd backend
pdm venv create --name django5 -p 3.12     # one-time setup
pdm use -p .venv-django5                   # bind pyproject.toml to the venv
pdm install                                # populate it from pdm.lock
pdm run python -c "import django; print(django.get_version())"   # MUST print 5.2.x
pdm run python manage.py test --keepdb
```

To switch back to a 4.2 branch:

```bash
cd backend
pdm use -p .venv-django4                   # (or: source .venv-django4/bin/activate)
pdm run python -c "import django; print(django.get_version())"   # MUST print 4.2.x
```

`pdm.lock` is checked in and is authoritative for the venv that the current branch expects. **Do not delete `pdm.lock` to "rebuild it"** - it must be regenerated by `pdm lock` (or `pdm update`), not deleted.

### The classic symptom of being on the wrong venv

You switched to the 5.2 branch, ran `pdm run python manage.py test`, the tests passed, and you assumed everything was fine. The CI was red, but your local check was green. **You were on the wrong venv.** The 5.2 branch's `pdm.lock` is in the working tree, but `pdm run` defaults to whichever venv is named in `pyproject.toml` - which on the 4.2 venv is still pointing at 4.2 packages.

**Always run this before any backend command on a freshly-checked-out branch:**

```bash
pdm run python -c "import django; print(django.get_version())"
```

If the printed version doesn't match the branch, you are on the wrong venv. Switch with `pdm use` (or activate directly: `source .venv-djangoN/bin/activate` on Linux/macOS, `.venv-djangoN\Scripts\activate` on Windows).

## Devcontainer

The devcontainer is defined in `.devcontainer/Dockerfile` and `.devcontainer/docker-compose.yml`. It does not need code changes for Django version upgrades - the Python version is set in `devcontainer.json` (currently 3.12), and the system packages installed in the Dockerfile (`postgresql-client`, `gdal-bin`, `libgdal-dev`, `libproj-dev`) are at distro versions that meet the GDAL >= 3.1 / GEOS >= 3.10 floor for Django 5.2.

What the devcontainer does need after a Django upgrade:

1. **Rebuild the container**: VS Code -> Command Palette -> "Dev Containers: Rebuild Container". This re-runs the Dockerfile and re-mounts the workspace.
2. **Create the venv inside the container**: open a terminal in the devcontainer and run the venv-per-Django workflow above.
3. **Verify the venv**: `pdm run python -c "import django; print(django.get_version())"` must print the expected version.

## Local dev machine (macOS or Linux, not devcontainer)

Same workflow as the devcontainer, but you manage the venvs and the system packages yourself.

### System packages

`start_backend.sh` (in the repo root) installs the system packages Climate Connect needs: `binutils libproj-dev gdal-bin` and friends. **This is also the production startup script** (per README "Deploy" section) - it runs `apt-get update && apt-get install` on every App Service cold start. If you are on macOS with Homebrew, the equivalent is:

```bash
brew install postgis gdal proj
```

### Python and venvs

```bash
# Optional: pin Python 3.12 via pyenv or asdf if not system default
python3.12 -m venv backend/.venv-django5
source backend/.venv-django5/bin/activate
pip install -U pdm
cd backend
pdm install
pdm run python -c "import django; print(django.get_version())"   # 5.2.x
```

Add `backend/.venv-django*/` to your global gitignore (`~/.gitignore_global` or similar) so you do not accidentally commit a path that should be local.

## Manual system dependencies that PDM does not handle

PDM handles everything in `pyproject.toml` / `pdm.lock` automatically. The following are **not** handled by PDM and require manual installation by each developer:

| Dependency | Why | Install (Debian/Ubuntu) | Install (macOS) |
|---|---|---|---|
| `gdal-bin` / `libgdal-dev` | GDAL CLI tools and headers for `django.contrib.gis` | `apt-get install gdal-bin libgdal-dev` | `brew install gdal` |
| `libproj-dev` | Cartographic projections library | `apt-get install libproj-dev` | `brew install proj` |
| `binutils` | Provides `objdump` and other utilities used at build time | `apt-get install binutils` | bundled with macOS dev tools |
| `postgresql-client` | `psql` CLI for connecting to local Postgres | `apt-get install postgresql-client` | `brew install libpq` and add to PATH |
| `redis-tools` | `redis-cli` for inspecting local Redis | `apt-get install redis-tools` | `brew install redis` |
| `python3-venv` | `venv` module for creating virtualenvs | `apt-get install python3-venv` | (bundled with python.org installer) |

If you hit a fresh-venv `ImportError` or `OSError: [Errno 2] No such file or directory` that is not a known Django issue, this table is the first place to look. If you find a missing dependency that is not listed here, **add it to this table** so the next person doesn't trip on the same thing.

## Broken venv recovery

If a `pdm install` fails on an existing venv (e.g. because the old venv was created with `pdm<2.10` and the lockfile format changed, or because you ran a half-completed upgrade), the nuclear option is:

```bash
cd backend
# Destroy the broken venv; keep the lockfile
rm -rf .venv .venv-django4 .venv-django5
pdm venv create -p 3.12
pdm install
pdm run python -c "import django; print(django.get_version())"   # verify
```

**Do not do this on a shared CI machine or in the devcontainer** unless you know what you are doing. Always preserve `pdm.lock`.

## Running tests

```bash
cd backend
pdm run python manage.py test --keepdb
```

The `--keepdb` flag reuses the test database across runs and avoids interactive prompts about creating/destroying it. Tests require **PostgreSQL on port 5432** and **Redis on port 6379** to be running. If either is not running, stop and start it - do not work around infrastructure failures by modifying test code.

For a single test file or test class:

```bash
pdm run python manage.py test <file_path> or <file_path + class_name>
```

### With deprecation warnings

During or after a Django upgrade, run the test suite with `-Wa` to surface deprecation warnings that may now be errors in the new version:

```bash
pdm run python -Wa manage.py test --keepdb
```

Treat any `RemovedInDjangoXXWarning` or other deprecation warning as a real compatibility regression and fix it before merging.

## Formatting and linting

```bash
cd backend
make format                # black + isort over the whole tree
make lint                  # ruff
```

Always run `make format` before committing. The CI runs the same commands; if you skip it locally, the CI will fail.

## Common gotchas

- **Wrong venv after `git checkout`**: see "The classic symptom of being on the wrong venv" above. Run the one-liner to verify.
- **`pdm install` fails with "lockfile is inconsistent"**: you may have edited `pyproject.toml` without running `pdm lock`. Run `pdm lock` to regenerate.
- **PostGIS not loaded**: `CREATE EXTENSION postgis;` in the local Postgres database. See README "Manual Setup" for details.
- **GDAL not found on Linux**: install `libgdal-dev` (see "Manual system dependencies" above). The `gdal-config` binary is the surest sign that GDAL is properly installed.
- **`psycopg2` import error after a Postgres upgrade**: rebuild the venv (`pip install --force-reinstall psycopg2-binary`).
